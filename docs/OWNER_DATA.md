# 회원 정보와 운영 권한

## 목표와 정확한 경계

현재 합의는 **개발자가 배포·클라우드 유지보수·백업을 맡고, 사장님이 유일한 앱 관리자로 회원 승인과 일정을 운영하는 방식**입니다. 개발자에게 클라우드·배포 기술 권한이 남아 있으므로 개발자가 데이터에 완전히 접근할 수 없다고 약속하지 않습니다. 클라우드 계정 이전은 출시 필수가 아닙니다.

서비스를 실행하는 프로그램과 클라우드 제공자는 필요한 데이터를 처리합니다. 회원도 로그인 후 본인 정보를 볼 수 있습니다. 여기서 '사장님만 관리'는 앱의 관리자 기능을 사장님만 사용한다는 뜻입니다. 클라우드 유지보수 권한까지 제거했다는 뜻은 아닙니다.

## 무엇을 어디에 두는가

| 항목 | 저장 위치 / 운영 담당 | 앱에서 보는 사람 |
|---|---|---|
| 이름·전화번호·아이디·가입일·승인 상태 | 운영 Cloudflare D1, 개발자 유지보수 | 본인 및 사장님; 전체 목록은 사장님만 |
| 예약·휴무·변경 기록 | 운영 Cloudflare D1, 개발자 유지보수 | 회원은 자기 예약, 사장님은 운영에 필요한 전체 |
| 비밀번호 검증 정보 | 운영 Firebase Authentication, 개발자 유지보수 | 앱은 비밀번호의 일치 여부만 사용; 원문 조회 기능 없음 |
| 세션·초기화 토큰 | D1에는 해시만 저장 | 원문은 해당 브라우저 또는 한 번 표시한 초기화 링크 |
| 운영 비밀값 | 운영 Cloudflare의 암호화된 설정, 개발자 관리 | 앱 화면에 노출하지 않음 |
| CSV·DB 백업 | 비공개 저장 위치; 운영 백업은 개발자가 관리 | 업무상 필요한 담당자만 |
| 개발 데이터 | 별도 미리보기 DB | 가상 이름·전화번호만 사용 |

비밀번호 초기화는 회원 행의 버튼과 상태로 표현합니다. 비밀번호 원문·해시·초기화 토큰을 회원 목록이나 Sheets에 내보내지 않습니다. Firebase에는 실제 이름·전화번호를 복제하지 않고, 앱 아이디를 변환한 이메일 형태의 별칭을 사용합니다. 실제 이메일 수신함이나 이메일 인증은 필요하지 않습니다.

## 향후 완전한 권한 분리를 원할 때 — 선택 사항

아래는 현재 운영 합의가 아니라, 나중에 개발자의 기술 접근까지 없애기로 결정한 경우의 별도 인수인계 방식입니다. 이번 파일럿이나 출시를 위해 먼저 수행할 필요는 없습니다.

1. 사장님이 Cloudflare와 Firebase 계정을 직접 소유하고 계정 복구 수단을 보관합니다.
2. 사장님이 운영용 GitHub 저장소를 소유합니다. 개발자는 개발 저장소에 수정본을 만들고, 사장님이 확인한 버전을 운영 저장소에 반영합니다.
3. 개발자에게 운영 Cloudflare·Firebase IAM·D1·로그·비밀값·백업 접근권한이나 운영 저장소 쓰기 권한을 주지 않습니다. 공유 관리자 계정도 만들지 않습니다.
4. 운영 Pages는 사장님 통제 저장소의 운영 브랜치만 배포합니다. 개발자 저장소에서 운영으로 자동 배포하거나 개발자가 호출할 수 있는 배포 훅을 두지 않습니다.
5. 미리보기에는 운영 DB·Firebase 서비스 계정·운영 비밀값을 연결하지 않습니다. 별도 시험 프로젝트나 로컬 가상 인증기만 사용합니다.

Cloudflare 문서상 Worker 배포 권한은 연결된 D1 자체의 권한과 별개입니다. 따라서 DB 화면 접근만 막고 코드를 배포할 권한을 주면 프로그램을 통해 데이터를 읽을 여지가 남습니다. 위 구성은 그 권한 경로를 분리하기 위한 판단입니다. [공식 권한·bindings 설명](https://developers.cloudflare.com/workers/authorization/#bindings)

GitHub 무료 개인 비공개 저장소를 이용할 수 있지만 비공개 저장소의 보호 브랜치 기능까지 무료라고 가정하지 않습니다. 운영 저장소에 개발자 쓰기 권한을 주지 않고 사장님이 업데이트를 가져오는 방식은 유료 브랜치 보호에 의존하지 않습니다. [GitHub 보호 브랜치 지원 범위](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

이 방식에서는 사장님이 운영 계정 설정·배포 승인·백업을 맡습니다. 개발자가 데이터를 볼 수 없으면서 운영 서버를 무제한 수정하고 장애를 대신 조사할 수 있다고 약속할 수는 없습니다. 문제는 가상 데이터로 재현하거나 사장님이 개인정보를 가린 오류 자료로 설명합니다.

## Google Sheets 사용

이번 변경은 **D1을 원본 DB로 유지하고 회원 CSV를 사장님 개인 시트에 가져오는 방식**을 제공합니다. 사장님이 Sheet를 공개하거나 개발자와 공유할 필요가 없습니다. 가져올 때 전화번호 열은 텍스트 형식으로 두어 앞자리 0을 보존합니다. 시트는 수동으로 받은 시점의 사본이며 자동 동기화하지 않습니다.

예약 원본을 동시에 수정 가능한 시트와 D1 두 군데에 두지 않습니다. 예약 확정은 D1의 제약·트리거로 겹침과 하루 한도를 검사합니다. [D1의 batch 및 트랜잭션 동작](https://developers.cloudflare.com/d1/worker-api/d1-database/)

Google Sheets로 원본을 만드는 것 자체는 가능합니다. Apps Script를 소유자 권한으로 실행하고 모든 예약 쓰기에 같은 잠금을 적용할 수 있습니다. 다만 시트를 직접 편집하는 경로는 스크립트 잠금을 따르지 않으며, 여러 요청에 걸친 '빈 시간 확인 → 쓰기'는 개별 API 요청의 원자성만으로 보호되지 않습니다. 지금은 추가 동기화·잠금 경로를 만들 이유가 적어 이 방식을 택하지 않았습니다. [Apps Script 실행 권한](https://developers.google.com/apps-script/guides/web) · [LockService](https://developers.google.com/apps-script/reference/lock/lock-service) · [Sheets API 요청 제한과 원자성](https://developers.google.com/workspace/sheets/api/limits)

## 인수인계할 자료

현재 인수인계에는 운영 주소, 관리자 아이디 보관 방법, 회원 승인·일정·공유 안내, 유지보수 연락 방법을 전달합니다. 개발자는 운영 저장소·클라우드 설정·백업과 복구 절차를 관리합니다. 계정 소유권과 기술 권한의 이전은 추후 필요할 때 별도로 정합니다. 실제 비밀값을 GitHub나 대화에 붙여넣지 않습니다. 수집 목적·보관 기간·삭제 요청 연락처는 실제 매장 운영에 맞춰 정해 사이트 이용 안내에 반영하는 배포 전 확인 사항입니다.
